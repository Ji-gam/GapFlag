## 1. 목적 및 배경

### 1-1. 해결하려는 문제

동물약 개발기업 R&D팀 연구원이 후보 성분의 "위험(레드플래그)"과 "기회(연구 공백)"를 판단하려면 openFDA·Open Targets·Green Book·EPO·Europe PMC·ClinicalTrials.gov 등 서로 다른 소스를 개별 조회하고 수작업으로 대조해야 한다. 인체 전용 상용 DB(Cortellis 등)는 종(species) 특이적 위험을 반영하지 않는다.

### 1-2. 이번 MVP에서 검증할 가설

동물약 개발기업 R&D팀 연구원은 성분 단위로 위험×기회를 한 화면에서 비교하고 근거를 확인하면, 기존 방식(개별 DB 수작업 대조)보다 유용하다고 느끼고 다시 사용하고 싶어할 것이다.

### 1-3. 목표 사용자

동물약 개발기업 R&D팀에서 신약 후보 성분을 초기 스크리닝하는 연구원 1명(대표 페르소나). 로그인·계정 개념 없음(단일 사용자용 조회 도구).

## 3. 범위

### 3-1. 포함 범위 (In Scope)

- 성분명 검색·조회 (사전 등록 목록 대조)
- 위험지수·기회지수 계산 (R1·R2·O1 기반, NULL 허용, 커버리지 % 산출)
- 2×2 위험×기회 매트릭스 화면 (인라인 SVG)
- 성분 상세 + 근거 카드 화면 (구성요소별 출처 링크, NULL 항목 회색 표시)
- 배치 데이터 수집 스크립트 (`scripts/build_cache.py` 수동 실행)

### 3-2. 제외 범위 (Out of Scope, 이번 MVP에서 구현하지 않음)

| 항목 | 제외 사유 |
|---|---|
| S3 후보 비교 화면 | 잘라내는 순서 1순위 (`CLAUDE.md`) |
| 실시간 외부 API 조회 | 화면은 DB만 읽는다는 원칙 |
| EPO 특허 밀집도(R4) | 계정·키 발급 지연 리스크 |
| ~~Green Book 기반 R3·O3~~ | 구현 완료 (2026-09-04) — 이 행은 이력용으로 남김 |
| 사용자 계정/로그인 | `auth_kit` 미사용, MVP는 단일 사용자용 |
| 성분 동의어 사전 자동화 | 확정된 요구사항 없음 |
| 다국어 지원 | 확정된 요구사항 없음 |
| React 프론트엔드 | Jinja2 서버 렌더링으로 대체(`MVP_SCOPE.md` §2-3) |
| Celery/Redis/APScheduler 자동 수집 | 수동 배치 실행으로 대체(§2-7) |

## 4. User Flow

```
[성분 검색 화면]
   성분명 입력 또는 목록 선택 + 종(개/고양이) 선택
        │
        ▼
[처리] 성분명 정규화 → DB 조회(R1·R2·O1 원자료) → 지수 계산(NULL 제외, 커버리지 산출)
        │
        ▼
[2×2 매트릭스 화면 (S1)]  사분면 위치 + 위험지수·기회지수·커버리지 표시
        │  마커/성분 클릭
        ▼
[성분 상세·근거 카드 화면 (S2)]  구성요소별 카드(값·출처·요약·원문 링크), NULL은 회색 표시
```

## 5. 기능 요구사항

### FR 우선순위 정의: P0=필수(없으면 가설 검증 불가), P1=있으면 좋음(잘라도 데모 가능)

#### FR-01 (P0) 성분명 검색·조회

| 항목 | 내용 |
|---|---|
| 설명 | 사용자가 성분명을 입력하거나 사전 등록된 목록에서 선택 |
| 입력 | 성분명(문자열, 자유 텍스트 또는 목록 선택), 종(`dog` \| `cat`) |
| 처리 | 성분명 정규화(대소문자·공백 정리) 후 `compounds` 테이블에서 일치/부분일치 검색 |
| 출력 | 일치하는 성분 목록(0건이면 "등록된 성분이 아닙니다" 안내) |
| 예외 | 빈 입력값 제출 시 검색 버튼 비활성 또는 안내 메시지, 결과 0건 시 안내 메시지 |

#### FR-02 (P0) 위험·기회 지수 계산

| 항목 | 내용 |
|---|---|
| 설명 | 선택된 성분·종의 R1·R2·O1 원자료를 산식에 따라 지수로 환산 |
| 입력 | `compound_id`, `species` |
| 처리 | `app/core/utils/scr_index.py`(순수 함수, I/O 금지)에서 아래 산식으로 계산 |
| 출력 | `{ risk_index: float\|None, opportunity_index: float\|None, risk_coverage: float, opportunity_coverage: float }` |
| 예외 | 구성요소 전부 NULL이면 지수 자체도 `None`, 커버리지 0%로 반환 (0점으로 치환 금지) |

**지수 산식** (`CLAUDE.md` 기준):

```
위험 지수 = Σ(wᵢ × Rᵢ) / Σ(wᵢ)     [MVP: R2만 활성, R1·R3·R4는 NULL이면 제외]
기회 지수 = Σ(wⱼ × Oⱼ) / Σ(wⱼ)     [MVP: O1만 활성, O2·O3는 NULL이면 제외]

NULL인 구성요소는 분자·분모 모두에서 제외한다.
커버리지 = 값이 있는 구성요소 수 / 전체 구성요소 수(위험 4개, 기회 3개 기준)
```

기본 가중치: 위험 R1~R4 각 25 / 기회 O1=40, O2=30, O3=30. 사용자가 화면에서 조정 가능해야 하며, 산식은 제품 안에서 공개한다(§8 화면 요구사항 S0 참고, P1).

#### FR-03 (P0) 2×2 위험×기회 매트릭스 표시 (화면 S1)

| 항목 | 내용 |
|---|---|
| 설명 | 선택 성분의 위험지수(X축)·기회지수(Y축) 위치를 인라인 SVG 매트릭스에 마커로 표시 |
| 입력 | FR-02의 계산 결과 |
| 처리 | 사분면 판정(위험 임계값·기회 임계값 기준 4분류) 후 SVG `<circle>` + `<title>` 툴팁 렌더링 |
| 출력 | 사분면 라벨(예: "비어 있는 이유가 있음"/"우선 검토"/"회피"/"경쟁 구간"), 위험지수·기회지수·커버리지 % |
| 예외 | 지수가 `None`(커버리지 0%)이면 매트릭스에 위치를 표시하지 않고 "판단할 데이터가 부족합니다" 안내 |

#### FR-04 (P0) 성분 상세 + 근거 카드 표시 (화면 S2)

| 항목 | 내용 |
|---|---|
| 설명 | 구성요소별(R1·R2·O1, 그리고 미구현된 R3·R4·O2·O3도 카드 자리는 유지) 근거를 카드로 표시 |
| 입력 | `compound_id`, `species` |
| 처리 | `compound_evidences` 조회, 값이 NULL인 카드는 회색 스타일 적용 |
| 출력 | 카드별 값·출처명·요약·원문 링크, NULL 카드에는 "데이터 없음 — 위험이 없다는 뜻이 아닙니다" 문구 |
| 예외 | 원문 링크가 없는 경우 링크 비활성화 처리 |

#### FR-05 (P0) 데이터 없음(NULL) 원칙 적용 — 횡단 요구사항

모든 화면·API·DB에 공통 적용되는 원칙이며 개별 화면 요구사항이 아니라 시스템 전역 제약이다.

- 데이터 없음은 `None`이며 절대 0으로 치환하지 않는다.
- 점수 컬럼은 전부 nullable. 0점("확인했고 위험 없음")과 NULL("확인하지 못함")은 다른 의미.
- 지수 계산 시 NULL 구성요소는 분자·분모 모두에서 제외, 커버리지 %를 함께 표시.
- 원본 API 응답(raw JSON)을 DB에 함께 저장(재계산 가능하도록).
- 화면은 DB만 읽는다 — 화면에서 외부 API 직접 호출 금지.

#### FR-06 (P1) 데이터 배치 수집

| 항목 | 내용 |
|---|---|
| 설명 | `scripts/build_cache.py`를 수동 실행해 openFDA(R2)·Open Targets(R1)·Europe PMC(O1) 데이터를 수집·정규화 후 DB에 저장 |
| 처리 | `services/src_openfda_service.py`, `services/src_opentargets_service.py`, `services/src_europepmc_service.py` 각각 dict 반환(외부 API 호출은 `requests`/`httpx`만 사용) |
| 예외 | 외부 API 실패 시 해당 구성요소는 NULL 유지, 배치 실행은 중단하지 않고 로그로 남김 |
| 테스트 | 외부 API 연동 코드는 `app/tests/fixtures/`의 저장된 응답으로 테스트(실 API 호출 금지) |

#### FR-07 (P1) 산식·가중치 공개 및 조정 (화면 S0)

| 항목 | 내용 |
|---|---|
| 설명 | 소개·데이터 출처·산식을 공개하는 화면. 가중치를 사용자가 화면에서 조정 가능 |
| 비고 | MVP 필수 화면 3개(검색/매트릭스/상세)에는 포함되지 않는 P1 항목. 없어도 가설 검증 가능하므로 잘라도 됨 |

## 7. 데이터 요구사항

### 7-1. 입력 데이터

| 항목 | 타입 | 필수 | 비고 |
|---|---|---|---|
| 성분명 | 문자열 | Y | 자유 텍스트 또는 목록 선택 |
| 종 | `dog` \| `cat` | Y | 종간 대사 차이 반영이 핵심 차별점 |

### 7-2. 시스템 보유 데이터 (모델 개요)

`docs/MVP_SCOPE.md` §4-2의 4개 모델을 그대로 따른다. 상세 컬럼은 담당자(이은호)가 `app/models/cmp_models.py`에서 확정하되, 아래 원칙을 반드시 지킨다.

| 모델 | 목적 | 비고 |
|---|---|---|
| `Compound` | 성분 기본정보(성분명, 등록 목록) | PK=`id`, 성분명 유니크 |
| `CompoundScore` | 성분×종별 위험/기회 지수 값 | 점수 컬럼 전부 nullable |
| `CompoundEvidence` | 구성요소별 근거(값·출처명·요약·원문URL·raw JSON) | 원본 API 응답 함께 저장 |
| `SpeciesAlert` | 종별 위험 신호(동물이상반응 등 원자료) | R2 등 종 특이 데이터 |

공통 DB 규칙(`CODING_RULES.md` §12): 테이블명 snake_case 복수형, PK는 `id`, FK는 `{참조테이블단수}_id`, `created_at`/`updated_at` 필수, Alembic으로만 마이그레이션(수동 ALTER 금지, 리비전 생성은 이은호만).

## 9. API 요구사항 (참고 — HTML 페이지 라우터 기준)

MVP는 JSON API가 아닌 Jinja2 서버 렌더링 페이지로 제공되지만, `CODING_RULES.md` §11 규칙에 맞춘 라우트 설계는 아래와 같다. 추후 React 전환 시 동일 Service 계층을 재사용해 `/api/v1/...` 엔드포인트만 얇게 추가한다(`MVP_SCOPE.md` §2-3).

| 라우트 | 메서드 | 화면 | 설명 |
|---|---|---|---|
| `/compounds` | GET | S-검색 | 검색 화면 렌더링, `?q=` 쿼리로 목록 필터 |
| `/compounds/{compound_id}/matrix` | GET | S1 | 지수 계산 후 매트릭스 화면 렌더링(`?species=dog\|cat`) |
| `/compounds/{compound_id}/detail` | GET | S2 | 근거 카드 화면 렌더링(`?species=dog\|cat`) |

에러 처리(`CODING_RULES.md` §9): 의도된 실패는 사람이 읽을 문장으로, 존재하지 않는 성분명 조회 시 404 페이지 또는 안내 메시지로 처리(예외를 조용히 삼키지 않음).

## 10. 수용 기준 (Acceptance Criteria)

MVP는 아래를 모두 만족해야 완료로 간주한다.

- [ ] AC-01: 사용자가 성분명을 검색해 목록 또는 상세로 이동할 수 있다
- [ ] AC-02: carprofen(또는 동등한 대표 성분)/dog 조합에서 R1·R2·O1 기반 위험지수·기회지수·커버리지가 정상 계산되어 매트릭스에 표시된다
- [ ] AC-03: 값이 NULL인 구성요소는 0으로 표시되지 않고 회색 + "위험이 없다는 뜻이 아닙니다" 문구로 표시된다
- [ ] AC-04: 근거 카드에서 출처 링크를 클릭하면 원문(또는 원문 예시 URL)으로 이동한다
- [ ] AC-05: 모든 화면 하단에 면책 문구가 표시된다
- [ ] AC-06: 화면은 외부 API를 직접 호출하지 않고 DB만 읽는다(배치 수집 결과만 사용)
- [ ] AC-07: `.env`의 `DATABASE_URL`을 MySQL로 바꿔도 코드 변경 없이 3개 화면이 정상 동작한다
- [ ] AC-08: `uv run pytest -v`, `uv run ruff check .`, `uv run mypy .` 모두 통과
- [ ] AC-09: 외부 API를 전부 차단한 상태(캐시만으로)에서 전체 시연이 완주된다
- [ ] AC-10: (정성적 성공 기준, 사용자 테스트 시 관찰) 사용자가 매트릭스를 보고 별도 설명 없이 "위험은 낮은데 아직 공백이 크다" 같은 해석을 스스로 말하고, 재사용 의향을 보인다 — 구체적 수치 기준은 [추가 검증 필요]

## 11. 미완성 구성요소 처리 (Tier2 stub 패턴)

EPO 키 발급이 늦거나 Green Book 파싱이 끝나지 않으면, DTO와 Router는 최종 형태로 두고 Service 내부만 `None` 반환 stub으로 둔다. 프론트(템플릿)·API 계약은 무변경. §5 FR-05의 NULL 설계가 이 안전장치 역할을 한다.

**뒤처질 때 잘라내는 순서**: ① S3 비교 화면 → ② 특허(EPO, R4) 구성요소(가중치 재분배로 흡수). Green Book 파싱(R3·O3)은 구현 완료되어 목록에서 빠짐.

**절대 버리지 않는 것 3가지**: 2×2 매트릭스 / 근거 카드와 원문 링크 / "데이터 없음" 회색 표시.
